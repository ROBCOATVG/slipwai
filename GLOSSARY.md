# The words slipwai uses

Every name in slipwai comes from the slipway and the harbour. Read this first. Everything else in the
repository uses these words without explaining them again.

Nothing in version 2 is called a workstation, a workstream, a lane or a runner. Where something here names
a version 1 idea, it uses version 1's own name for it and says so.

| Word | Meaning | Version 1 name, where one existed |
|---|---|---|
| **Keel** | The core of slipwai: the questions it asks, the code that writes a project, the toolkit, the adoption path, and the delivery loop. Every package attaches to the keel | "core", "core driver" |
| **Language** | A package that holds every answer for one language family, with a thin framework package for each framework of that family. Example: `java` is a family, `java-quarkus` is a framework of it | Same word |
| **Extension** | A package of developer tooling that a project chooses to add. Example: `codegraph` | Same word |
| **Chandlery** | The index of packages that slipwai can install: languages and extensions, each with a version, a compatibility range, a checksum, a publisher and a one-line description. `slipwai search <term>` finds packages across every channel; `slipwai show <name>` describes one; `slipwai install <name>` installs it | "marketplace", "index" |
| **Slice** | One unit of product work that an actor can use when it is done. Unchanged from version 1 | Same word |
| **Fairway** | One bounded context's slices, in split order, with one release flag and one holder. The fairway is the unit of scope, of ownership and of release. Several fairways run side by side into the same harbour. A vessel keeps to its own fairway | "value stream", "workstream" |
| **Berth** | The provisioned place where one captain works: a sandbox or container, a git worktree, environment variables, an allocated block of ports, a database, and scratch directories. A berth holds no cloud or forge credential. `slipwai berth add`, `slipwai berth status` and `slipwai berth remove` manage berths | "workstation", "lane" |
| **Captain** | The one in charge of one fairway, in both modes. There is one captain per fairway, and it is two things. **The captain program** is underneath and always runs: it reads the logs, works out the state of the fairway from the logs and trunk, gives clearance, claims a slice, starts its session, enforces every stage boundary, holds the session slots, the stage budgets, the retry ceiling and the gate, asks for every merge, and is the one writer of the deck log. **The captain agent** sits on top where it can: one agent session per fairway that makes a handful of choices — which cleared slice starts next; after a failed gate, retry with what note or park with what reason; what to do about a stuck slice (message it, interrupt it, pause, stop or park it, or tell the person); where something a person said to the stream goes — and, where it is asked, rules on a permission a slice's session wants outside its berth (a read inside the project, nothing else). It acts only by giving orders through the project's own `scripts/agents/orders.py`; the program checks each order against the rules, does it or refuses it, and writes why. Where the agent says nothing within its bound, orders something not allowed, or cannot be run, the program makes that one choice by its fixed rule and tries the agent again at the next event, so a fairway always runs. The agent runs only where its session can be held over the Agent Client Protocol, which confines it to reading and running `orders.py`; on a harness with no proven launch over the protocol the fairway runs on the program alone and says so. It never answers a product question: a question a slice's session asks mid-turn is declined and goes down the deck log's `question` path to the skipper or a person, unless `harbour.json`'s `captain.answers` is turned on, when each answer is written as a `decision` for a person to review. Under `/sail` every question and park comes back to the person, and every demo where `demos` says a person accepts them. Under `/cruise` the skipper answers and the hand demos | "runner", `cruise.py run` |
| **Harbourmaster** | The part the captains share, one process per machine. It allocates local berths, writes only that machine's harbour log, syncs logs and in-flight branches, draws the fleet board and the bridge, holds the flags, and answers the telegraph. The merge is serialised through `refs/slipwai/merge`. Under `/sail` it runs inside the person's session; under `/cruise` it runs on its own. It performs each merge a captain asks for, one at a time, after running the full gate, and chooses none | "integrator" |
| **Deck log** | A fairway's own append-only log at `.slipwai/run/logs/<feature>/<fairway>.jsonl`, ignored by git and written by that fairway's captain program. Three other hands append to it through the project's own scripts: `/cruise-tell` writes a person's `told`, a slice's session writes a `told` to hand something back, and the board writes the `read` receipts and `need-done` ticks the board writes when a person presses Done, marks a decision read or ticks a need. What a person says to a slice or a captain on the board goes to a conversation's inbox, never to this log. The harbourmaster syncs it between machines through `refs/slipwai/logs/<fairway>`, never through trunk. Its kinds are `claimed`, `mark-set`, `demo`, `accepted`, `demo-due`, `merged`, `decision`, `question`, `told`, `read`, `heartbeat`, `request`, `berth-request`, `stowed`, `taken-over`, `yielded`, `stopped`, `parked`, `need-done`, `seeded`, `dispatched` and `noted`. A reader that meets a kind it does not have refuses the line and stops the fold rather than skip it, so a board older than the log says the log cannot be read. A `parked` owes a `cleared` harbour receipt naming the fairway, the original park's timestamp and the answer; its wait clock runs until that receipt arrives. A park is a record: `cause`, one word from a closed set; `until`, the instant it lifts by itself; `needs`, one item per thing that has to change; `then`, what the fleet does once they are met | "stream log" |
| **Harbour log** | One append-only log per machine at `.slipwai/run/logs/harbour/<machine>.jsonl`, ignored by git and written only by that machine's harbourmaster. Every fairway reads all machines' logs folded by time; the older `.slipwai/run/logs/harbour.jsonl` is still read in that fold. Its kinds are `mark-set`, `flag-hoisted`, `flag-struck`, `berth-allocated`, `fires-banked`, `park`, `telegraph`, `granted`, `refused`, `cleared`, `need-met`, `told-met`, `trunk-red`, `trunk-green`, `fix-trunk`, `mend`, `mended`, `mend-failed`, `merge-taken-over` and `slots`. A captain never appends to it; the harbourmaster carries what other fairways need from each deck log and records the answers it owes | "cross-stream log" |
| **Chart** | The contracts, written before the split, as one committed file per feature: `specs/<feature>/chart.yaml`. The chart names the fairways, the marks each slice sets, the marks each slice steers by, and the paths each fairway owns. On the event-modelling profile `make chart` renders it from the event model and `check-chart` fails when the two disagree. On the standard profile a `/chart` stage writes it | "contract map", "streams manifest" |
| **Mark** | One published contract that another slice steers by: an event, a route, a schema or a port, typed. An event or a schema is typed with JSON Schema; a route is an OpenAPI operation; a port is a name with typed inputs and outputs. A mark is set once and never moved. The files that hold marks only grow | "contract entry" |
| **Clearance** | The rule that lets a slice start. A slice has clearance when every mark it steers by has been set by a slice that is planned or implemented. A slice sets its own marks itself, as its first stage, in its own worktree | "consumption gate" (issue #32) |
| **Pause** | Two things carry the word. A fairway's pause is a park that lifts by itself: the harness refused to run the session (`cause: limit`) or the park carries an `until` still ahead. Nobody is asked anything. The harbourmaster writes its `cleared` receipt when the time comes and lights the captain; `/cruise-tell` lifts it early. The board calls the stream `paused`, never `waiting on you`. A slice's pause is a hold placed through the slice's conversation, by a person or by its captain: the turn under way finishes, the session is kept and its slot is given back, and the slice waits until it is resumed | none |
| **Need** | One thing a park waits for, from its `needs` list: what has to change, who ticks it — the fleet through a `text` or `make` check against trunk, or a person on the board — and, once ticked, a `need-met` harbour receipt. A park whose needs all have receipts clears without anybody being asked | none |
| **`dispatched`, `noted`** | Two deck kinds the captain program writes. A `dispatched` line is one run of `/sail` for a slice, written when the run ends, with `free` where the run cost no attempt (a person's message or interrupt, a harness that would not run it, a stop of the fleet). The program counts them before every run: between a person's words to a slice it runs at most `2 × attempts + 1` that cost an attempt, whoever asks, and then parks the slice for a person. A `noted` line is news about the captain agent for a person to read — that it failed and the fairway runs on the program alone, or that its session was refused commands. Nothing waits on a `noted`: it is not a `told`, it owes no `read`, and it never holds a fairway | — |
| **Conversation** | What a person, a captain or the fleet says to one slice or one captain, in `.slipwai/run/talk/<fairway>/<slice>/` or `talk/<fairway>/_captain/`: an `inbox/` with one signed file per message, and a `thread.jsonl` that only the driver writes. A message is *Send* (it waits for the turn under way) or *Interrupt* (it cancels the turn and goes in at once), or a pause, a resume, a stop or a withdrawal. The board, the fleet's own programs and the MCP `tell` place messages here; nothing said on the board is written into a deck log | the `told` line the board used to write |
| **Driver** | The one thing holding a slice's session while the slice is worked, inside its captain's process. Over the Agent Client Protocol it is held open: one session, many prompts, with a retry or a message going in as the next prompt. It closes with the session's id saved while the slice waits (a park, a pause, a stop, a merge) and loads that session when the slice carries on, or starts a fresh one where the agent cannot load it; a review, an attack or the hand's walk always starts fresh. In print mode each run is a new session and messages go in with the next run's prompt, with no interrupt. The driver is the one writer of its conversation's thread. An idle driver holds no session slot | — |
| **Receipt** | Where a message stands, read from its inbox file and the thread and stored nowhere: *queued* (it may still be withdrawn), *held* (kept back from a slice at its merge, with why), *delivered* at the instant the driver records, *answered* with the reply, *delivered, not addressed* where the turn ended with no word about it — a quiet flag, never *Waiting on you* — and *not delivered* with why and **Send again** | the `read` line, for what the board said |
| **Hold** | What keeps a slice from carrying on until somebody lifts it: a pause or a stop placed through its conversation. A person's hold stands from the moment it is heard until a person resumes the slice, whatever ends the turn and whatever anyone else says meanwhile; a captain's pause or stop on top of it is not a second hold. A pause a captain placed is lifted only by a resume from that captain or a person — no timer and no harbour rule lifts it. A merge ends every hold. The word also names a message *held* at a slice's merge: from its merge request to the answer nothing is delivered to it | — |
| **Observable** | The first thing a person — or an external system a person can inspect — can judge: a screen, a read model under the API, an automation's side effect, an outbound translation. On the chart the `state-view`, `automation` and actor-facing `translation` slices; a `state-change` is observable only through one of them | "screen", "demo" |
| **Feedback point** | An observable a person is asked to judge, placed by what delaying the judgement would cost: the agent-made decisions it would test, the unmerged slices steering by its marks, the commitment points ahead of it, over what it costs to surface. `clearance.py --feedback` ranks them; a merge is not one | "demo stop" |
| **Given** | A record a slice's story (`try-it.json`) appends through the service's seed door before its steps, because the slice that would have written it is not built. Typed by the model, never sent through an HTTP route, and marked *given, not made* on the Try it card | "seed data", "fixture" |
| **Seeded** | The deck line that says a slice's story ran green against the app its berth runs, written by `try_it.py seed --slice` at the Demo rung. A slice with a story and no `seeded` line this turn parks at its gate | — |
| **Careen** | One hardening slice per fairway. It holds the findings below the severity bar and the work that stages stowed, which each slice writes into its capability's `stowed.md` and the harbourmaster carries into `fairways/<fairway>/careen.md` at the merge. The captain starts it as the fairway's last slice once every planned slice is merged, whatever the release state, so before any flag is hoisted. Its demo is: the findings are closed | "hardening slice" |
| **Stow** | What a stage does with its open work when it runs out of budget: it moves the work into the careen. Work is never dropped. A CRITICAL finding is never stowed | "backload" |
| **Telegraph** | The dial between speed and cost: the engine order telegraph on the bridge. A person rings it; the engine room answers by raising or lowering steam. Its positions are `full-ahead`, `half-ahead`, `slow-ahead`, `dead-slow` and `stop`. Each position sets, as a group, the nine numbers underneath it: how many boilers are lit, how many delegates a captain may run at once, the bunker per slice and per day, the stage budget, the severity bar, the unreviewed-decision ceiling, the wait bound and the attempts. The model role each stage uses is **not** one of them: a role per stage lives in `.specify/models.json`, is set by `/model-delegation-settings` and read by `scripts/agents/models.py`, and ringing the telegraph does not move it. `slipwai telegraph half-ahead` rings it. Each number underneath can also be set alone | "concurrency setting", "cost cap", "trim" |
| **Boiler** | One berth under steam. A lit boiler is a captain working. The telegraph says how many may be lit at once | "max concurrency" |
| **Bunker** | The coal store: the token budget, per slice and per day. Tokens are the coal. The pressure gauge on the fleet board shows the rate they burn at | "token budget", "cost cap" |
| **Bank the fires** | What the harbourmaster does when the bunker runs down faster than the telegraph position allows: it rings the position down one notch, which lowers every number together — delegates and boilers among them — and writes `fires-banked` with the step it rang and why. One notch at a time rather than straight to `stop`, because a run that stops dead loses what was in flight and a run that slows finishes it. A person stokes the fires back up | "throttle", "reef" |
| **Hoist, strike** | To hoist a flag is to turn a release flag on for real actors. To strike a flag is to remove it after it has been on everywhere for long enough. Only a person hoists | "turn on", "remove the flag" |
| **Pre-launch, pilot, live** | The three states of a product, recorded once in `project.json` as `state`. Pre-launch: no production yet, or one only the team sees. Pilot: a production with a known set of pilot users. Live: real users. The release mode follows from this state. Plain words on purpose: an earlier draft called them slipway, sea trials and in service, which read as decoration on a fact a person has to act on | "slipway", "sea trials", "in service", "beta", "GA" |
| **Release mode** | How dark a merge is. One of: open, keystone, flagged, promoted. Section 4, theme E, defines each | `release: flagged` |
| **Skiff, liner** | The two shapes of a cloud target. A skiff is one environment on the smallest managed compute and database, for a staff tool. A liner is today's full stack, for a product. Theme E defines both | one stack for every project |
| **Skipper, hand, bosun** | The three delegates inside one iteration. The skipper decides product questions. The hand runs the demo, and its verdict accepts a whole capability unless `.specify/cruise.json`'s `demos` says a person does. The bosun works round a block. Unchanged from version 1 | Same words |
| **Fleet board** | Every view of the harbour, meaning the agents at work: the berth table, the slice graph by fairway, the swimlanes with cost, the event feed, the pressure gauge and the bunker, and the inbox. Every view is computed from the logs and from `git rev-list`. The fleet board keeps no state of its own. `slipwai fleet` prints it. `slipwai fleet watch` keeps it live. The harbourmaster also renders it as a page | "fleet view", "multi-lane status", "dashboard" |
| **Bridge** | One product's own dashboard, as distinct from the fleet board, which is the harbour's view of the agents. The bridge shows where the product is (slipway, sea trials, in service), the release mode, how far along each fairway is, which flags are hoisted and where, what is deployed to each environment, what is waiting on a person, and what the product has cost so far. `slipwai bridge` prints it. The harbourmaster renders it to the project's Pages site next to the event model | `/where-are-we`, the demo stop's progress board, the event-model page |
| **Sail, cruise** | `/sail` is the main mode: a person is present, the whole fleet fans out across fairways, and every product question and park comes back to that person through the inbox — and every demo too where `demos` says a person accepts them; by default the film is there for them to comment on. `/cruise` is the same fleet with nobody at the keyboard: the skipper answers the questions and the hand runs the demos. Nothing else differs. The two words are a pair and are chosen to be one: somebody is at the wheel, or nobody is | `/drive`; and in version 1 only `/cruise` fanned out across a product |
| **The ladder** | The ordered stages of `/sail`. Section 5 draws it | Same word |
| **Rung** | How much of its past one service keeps, named for the step of the constitution's ladder it stands on: an outcome returned, in-process events, an outbox, or a durable log of everything that happened, which is event sourcing. A rung is per service, is answered on the `write-model` axis (`events` or `state`) beside the `persistence` axis that names the store, is recorded in `project.json`, and is the one answer about a service that cannot be walked back once it holds data. Event Modeling is the same on every rung; what changes is the write model. The convergence map (section 4) counts rungs too, on a different ladder — where an *adopted repository* stands on each axis of the keel's own shape — and the two never meet: no persistence row is added to that map, because a map row would say every service should climb to the log. Phase 15 | The `event-modelling` profile, which bundled the log with the model |
