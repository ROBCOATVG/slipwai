# Strategy playbook: in-place

In-place changes the system where it stands: it moves the one codebase up the platform ladder one rung at a time (language version, framework, packaging, runtime/container, host) and improves the delivery practices around it as it goes. There is one deployable and one codebase throughout, and no second system is ever built. The rule for a new feature: it lands in that one deployable, after the floor is green and after any security rung, it either waits for a rung that would rewrite its area or is fenced away from the doomed layer, and it never carries a platform change itself.

---

## 1. What it is

In-place is the conservative end of modernisation. In the AWS "7 Rs" vocabulary it is a sequence of small **replatform** steps that happen in the codebase, not at migration time. It ends with an optional **rehost** (the host rung). It sometimes uses **refactor** for one bounded part, such as replacing an end-of-life web framework. It is not **retain**, because retain means doing nothing. It is not a rewrite or a strangler either, because no second system is ever built. The bet is that the existing code is worth keeping and that the dangerous part is the platform under it, not the domain logic on top.

The unit of work is the **rung**. A rung moves one layer of the stack to one new version across the whole application, behind a green gate, in one slice or a short run of slices. Google's large-scale-change (LSC) practice is the model. Changes are generated by tooling, not typed by hand. They are split into independently committable shards. Every shard passes the tests. A cleanup phase then makes sure the old pattern cannot come back. The book's rule of thumb is that automation pays once a change needs more than about 500 edits. ([SWE at Google ch. 22](https://abseil.io/resources/swe-book/html/ch22.html))

### When it is right
- **The domain logic is broadly correct and valued.** Users complain about speed, security and deploy pain, not about what the system does.
- **The codebase is small to mid-sized** (up to a few hundred thousand lines) and has one deployable. Climbing the ladder across the whole app is tractable per rung.
- **Recipes exist for the rungs.** Java has OpenRewrite (language upgrades, Spring Boot, javax→jakarta, common ORMs). Python has `pyupgrade` and `django-upgrade`. .NET has the .NET Upgrade Assistant. Recipes turn rungs into mechanical LSCs.
- **The business needs features to keep flowing.** No one will fund a freeze, and no one will fund running two systems at once.
- **There is a security or support clock.** Examples: an EOL runtime, or a framework with a public remote-code-execution history. The fastest risk reduction is to patch the existing system, not to replace it.

### When it is wrong (warning signs)
- **The model itself is wrong.** Examples: wrong aggregates, a schema that cannot express the new business. Climbing the ladder only polishes the wrong thing. Consider `strangler` or `rewrite`.
- **There is no viable rung.** The framework has no supported successor and no recipe, for example a proprietary 4GL. The jump would be a rewrite of the UI layer anyway.
- **The codebase is many deployables with tangled shared libraries.** Then "one rung across the whole app" becomes a fleet-wide LSC that needs Rosie-style sharding. In-place still works there, but it is a programme, not an adoption.
- **The same rung keeps going red.** If a rung slice has been red for more than about 3 attempts or more than about a week, the rung is probably a rewrite in disguise.
- **Features keep forking around a rung.** "We'll do it after the upgrade" piles up. That means the rungs are too big, or the gate is not trusted.

## 2. What the ADR records

The accepted ADR carries `Strategy: in-place` plus these lines. The method reads them and they are checkable in the tree.

```
Strategy: in-place
Deployable: <the one artefact, e.g. app.war, a wheel, a container image>
Ladder:
  1 language: <current> -> <stepping stone(s)> -> <target LTS>   (recipe: <recipe id or tool>)
  2 framework: <web framework, DI/container, ORM: current -> stepping stone -> target>
               then <the namespace or major-version jump that must move together>
  3 packaging: <e.g. server-deployed archive -> self-contained executable>
  4 runtime: container image (<base image>)
  5 host: <target host>
  6 shape: toward Target, by reshaping this code (target-shape.md); last, once the finish line holds
Coupled rungs: <tuples that must move together, see "Coupled rungs and stepping stones">
Stepping stones: <intermediate versions that exist only to be passed through>
Feature interleave: rung-window | fence | either (see section 4)
Banned on entry: <APIs/frameworks new code may not use, e.g. the framework being removed, the old namespace after its jump>
Security clock: <CVE/EOL that sets pacing, e.g. web framework line EOL with known RCEs; runtime EOL>
Target: <the shape this code is reshaped toward, e.g. "modules in one deployable, hexagonal inside each — module map: <link>" | as-is> (target-shape.md)
Data: migration tool <Flyway|Liquibase|Alembic|EF migrations|…>, baseline = DB as it is on <date>
Finish line: <what "done" means, e.g. current LTS runtime, supported framework major, executable artefact, image, deployed by pipeline>
Owner of rung windows: <person who may pause features in an area>
```

Why each line matters:
- **Deployable** names the one artefact every rung must keep producing; smoke runs against it.
- **Ladder** is the ordered list of rungs and the recipe for each. The plan orders rung slices from it, and the board shows it as a column of rungs. Rung 6 (`shape`) comes last and only once the finish line holds.
- **Coupled rungs** lists the tuples that must move together. The gate checks the dependency tree against the tuple for the current rung, which stops rungs being skipped.
- **Stepping stones** names the intermediate versions that exist only to be passed through, so no one mistakes one for a target.
- **Feature interleave** sets the default rule for features that meet a rung: wait for the rung window, fence away from the doomed layer, or either, decided per feature.
- **Banned on entry** seeds the banned-API ratchet: what new code may not use from day one.
- **Security clock** sets pacing. It is why a security rung can jump ahead of ladder order and ahead of features.
- **Target** is the shape this code is reshaped toward in the last rung (`target-shape.md`). `as-is` means the ladder ends at the finish line.
- **Data** names the migration tool and the baseline date. Every schema change after it is a numbered migration.
- **Finish line** defines "done", so a rung cannot be finished on paper.
- **Owner of rung windows** names the person who may pause features in an area while a rung is open.

The method should refuse to plan rung slices when any of these are missing: `Ladder`, `Feature interleave`, `Data`, `Finish line`. `Coupled rungs` may be stated as `none`.

### Decision criteria
Write the answers into the ADR.

| Question | In-place if… |
|---|---|
| Is the domain behaviour worth preserving as-is? | Yes, mostly |
| Does each layer have a supported next version? | Yes, or a well-trodden replacement (an EOL web framework → its ecosystem's mainstream successor) |
| Does tooling exist for the rungs? | Recipes cover at least ~70% of edits |
| Can the app be started and exercised headless? | Yes, or it can be made to (smoke) |
| Can the business absorb short "rung windows" in which features in the touched area pause? | Yes |

### Coupled rungs and stepping stones
This is what the `Coupled rungs` and `Stepping stones` lines record. The ladder is not strictly separable, because rungs interact. Record them as tuples that must be true together:
- An old framework version may not run on a newer runtime at all (for example, it cannot read the newer bytecode or uses a removed API). Raising the runtime then forces a minimum framework version.
- A framework's new major often needs both a newer runtime and a new namespace or API generation, and its sibling libraries need the same. These form **one tuple**, and they move in one rung window.
- A current toolchain may refuse a very old language level. One legacy module can then block the whole build floor, so fix it in the build floor step (0.2), not in the language rung.

So the real order is a chain of **compatible tuples** (stepping stones), not "all of rung 1, then all of rung 2". The general shape is:
`(old runtime, old framework set)` → `(stepping-stone runtime, last compatible framework majors)` → `(target runtime, same frameworks)` → `(target runtime, new framework generation together)` → `(executable packaging)` → image → host.

## 3. Phases

Phase 0 is the floor and is strategy-independent. Phases 1 onward are where in-place differs: they are the rungs, in ladder order, with security rungs promoted to the front.

Every rung slice in phases 1 to 6 has the same shape:
1. Point the agent at the **recipe**, not the files. Run the recipe in dry-run mode, then for real (e.g. OpenRewrite `rewrite:dryRun` then `rewrite:run`; `pyupgrade --py3X-plus`; the .NET Upgrade Assistant). Commit the recipe output as its own commit, then commit the hand-fixes separately. Generated diffs are cattle: if the slice goes wrong, regenerate rather than patch by hand.
2. `make verify` green, with characterisation `.approved` files **unchanged**. Any approved-file change must be justified in the slice notes and approved by a person.
3. Run smoke on the new tuple.
4. Cleanup: add the old target or API to the banned list so it cannot creep back.
5. Bump the platform axis in the convergence map.

### Phase 0: make the old system safe

**0.1 Quick wins: secrets and committed build output.** Move committed secrets to environment or untracked config, with a `.env.example`. Rotate them, because history still holds the old values. Remove committed build output (`build/`, `target/`, `dist/`, compiled binaries) and `.gitignore` it. Turn hard-coded absolute paths into config keys with defaults.
- Who: agent does the edits. A person rotates the credentials, because only they can.
- Evidence: `git grep` for known secret patterns returns nothing outside `*.example`. No build output is tracked. A `secrets` check runs in `make verify` (gitleaks or a regex list). The rotation is recorded as a board item ticked by a person.
- Unblocks: everything. It also makes the repo safe to hand to the agent fleet.

**0.2 Build floor, up to date** (`build-floor.md`). The build meets the floor's eight criteria, and the toolset — build tool, wrapper, plugins, the runtime the build runs on — is brought fully current; the target is raised as high as the code allows today, and the ceiling and the rung that lifts it are recorded on the ADR's `Build:` line. Replace a hand-rolled build with vendored libraries by the ecosystem's standard dependency manager, invoked through a committed **wrapper** or lockfile (e.g. `mvnw`/`gradlew`, a Poetry or uv lockfile, a pinned SDK via `global.json`). Map each vendored library to a published coordinate and version, using checksums or the tool's analysis command to find the match. Anything with no coordinate goes into a local repository with a TODO. Keep the *same* library versions in this step and change only how they are resolved. Fix any module whose language level no current toolchain accepts: current compilers and interpreters drop very old targets, so such a module moves to the lowest level the current toolchain still supports. Caveat: moving to a current toolchain can **silently change the runtime target**. A build floor that compiles for a newer language level, or runs on a newer interpreter, is already a language rung for the code and libraries that run on it, and old libraries may fail to load or start. Treat this as the first coupled-rung decision and record it in the slice notes.
- Who: agent, with a `/survey` of the vendored libraries first.
- Evidence: the wrapper build succeeds on a clean checkout. The vendored library directory is gone. The produced artefact matches the old one (a diff of the bundled dependency list is empty except for intended changes). A `build-floor` line in the convergence map moves to `supported`.
- Unblocks: every recipe tool. Most recipe tools run as build plugins or against a resolvable dependency graph, so no build floor means no recipes.

**0.3 Prove it starts (smoke).** Add a `smoke` command that starts the deployable headless and checks that it comes up. Use an embedded server or a throwaway container. The database comes from Testcontainers, a docker-compose service, or a seeded copy. The check is an HTTP 200 on the landing page, a login, and one read of a known record.
- Who: agent writes it. A person supplies a sanitised DB snapshot if one exists.
- Evidence: `make smoke` exits 0 in CI. It is wired into `make verify`, or into a `verify-slow` lane that runs on every rung slice.
- Unblocks: any code change. No code change before smoke is green.

**0.4 Characterise (safety net).** Use Feathers-style characterisation tests, which pin what the code *does*, not what it should do. Write them around the areas the ladder will disturb (request handlers, persistence mappings, date and locale handling, anything reflective or dynamically loaded) and around the first feature's area. Prefer approval or golden-master tests (ApprovalTests: `.received` vs `.approved` files) over hand-written assertions. Scrub volatile values such as timestamps and IDs. Feathers' heuristic: characterise the area you will change, then the specific things you will change.
- Who: agent via `/characterise`. A person approves the first `.approved` files; approving is the act of agreeing "this is current behaviour, warts and all".
- Evidence: characterisation tests exist under the test tree. The `.approved` files are committed. The convergence map's `safety net` axis is at least `inventoried` for every area a rung touches.
- Unblocks: platform rungs. A rung's diff is judged by "characterisation unchanged".

**0.5 Data baseline.** Introduce a migration tool (Flyway, Liquibase, Alembic, EF Core migrations or similar). Generate a baseline migration from the **production schema as it is**, using the database's own schema-export tooling. Mark each existing environment as baselined so the history table records the baseline without executing it (`flyway baseline` in Flyway terms). Use automatic baselining only deliberately: Redgate warns that `baselineOnMigrate` removes the guard against migrating the wrong database. Fresh test databases run the baseline for real, so smoke and characterisation start from the same schema as prod. Turn off any ORM setting that alters the schema at startup (`validate` at most).
- Who: agent writes it. A person runs the baseline on the shared and prod databases.
- Evidence: the baseline migration file exists. CI builds a DB from it and smoke passes. No ORM auto-update or auto-create setting is enabled. The `data` axis is `supported`.
- Unblocks: any feature that changes the schema. Also the ORM upgrade in the framework rung, because the new version's schema validation is checked against a known schema.

**0.6 Gate and ratchet.** `make verify` = build, unit and characterisation tests, smoke (or the slow lane), lint/typecheck with a **ratchet** baselining existing findings, the secrets check, and a **banned-API ratchet** (seeded from `Banned on entry`; see "fence" in section 4). Work is trunk-based: rung slices land on main behind the gate, with no long-lived upgrade branches. DORA's Capital One case found weak test automation was what pushed teams back to long branches; the gate is what keeps trunk viable.
- Who: agent installs it.
- Evidence: `make verify` is green on main. The ratchet baseline file is committed. CI runs it on every PR.
- Unblocks: fleet slices (`/sail`, `/cruise`), and the first feature once its area is characterised.

### Phase 1: security rungs

**1.1 Read the security clock.** Find every layer with a known exploited CVE, or a library still on an EOL branch. Check the framework's own security bulletins and EOL page, and the dependency scanner's output, rather than assuming a version is safe because it is old enough to predate a famous CVE. Check vendor support tables, not community lore: dates differ by vendor for the same version.
- Who: agent runs the scanner and reads the bulletins; a person confirms the `Security clock` line.
- Evidence: the ADR's `Security clock` line names the CVEs/EOLs. A dependency CVE count ratchet is in the gate.
- Unblocks: the decision of which rung is promoted ahead of ladder order.

**1.2 Patch on the first stepping-stone tuple.** Run the rung (or rungs) that patch the security clock **before** the first feature, regardless of ladder order, because features add attack surface on an unpatched framework. Usually this is the first stepping-stone tuple: the runtime to its stepping stone, the web framework to its last patched major, the ORM to its last compatible major, as separate slices in one rung window, each with the rung slice shape above.
- Who: agent runs the recipes; the owner of rung windows opens the window.
- Evidence: the dependency tree shows the patched majors. The dependency scanner shows no critical CVEs (or they are ratcheted). Characterisation is unchanged and smoke passes on the new tuple.
- Unblocks: feature slices that require the patched layer.

### Phase 2: language

**2.1 Run on the new runtime.** Use the ecosystem's upgrade recipes, one LTS or stepping stone at a time. Illustrations: a Java runtime upgrade via OpenRewrite's `UpgradeToJava17`/`UpgradeToJava21` (from `rewrite-migrate-java`, which also adds the libraries that left the JDK); a Python 2→3 or 3.x→3.y move via `pyupgrade` plus `2to3`-era fixers; a .NET Framework → modern .NET move via the Upgrade Assistant. Pin the recipe tool's version and check the licence of each recipe pack. Split the language rung in two, and do this half first: *run* on the new runtime while keeping the old language level. This shows runtime breakage (reflection, internal APIs, removed standard-library modules, stricter encapsulation) separately from source changes. Run on a quiet trunk.
- Who: agent runs the recipe.
- Evidence: the runtime version reported in CI and smoke is the target. No escape hatches (such as opening internal modules) are added without a ticket. A tool that reports internal-API use is clean or ratcheted.
- Unblocks: 2.2, and any framework major that needs the new runtime.

**2.2 Raise the language level.** Raise the declared language level to the target, a current LTS.
- Who: agent runs the recipe.
- Evidence: the build declares the target level. Characterisation is unchanged and smoke passes. The old level is banned in the ratchet.
- Unblocks: the framework-generation tuple.

### Phase 3: framework

**3.1 Last compatible majors.** Order inside the rung follows the compatibility tuples. Typically the web framework, the DI/container framework and the ORM each move to the last major that still works on the old namespace or API generation.
- Who: agent runs the recipes.
- Evidence: the dependency tree shows the stepping-stone majors. Smoke passes.
- Unblocks: 3.2.

**3.2 The generation jump, together.** A single concentrated window moves the web framework, DI/container and ORM together to the new generation (in Java, the javax→jakarta jump that Spring Boot 3, current ORMs and current web frameworks all require; OpenRewrite's maintainers recommend running `JavaxMigrationToJakarta` first for non-Boot code). Adopt a new application framework without changing packaging first: wrap, then repackage. For example, Spring Boot's docs recommend producing a deployable WAR with `SpringBootServletInitializer` and the old XML config imported, then moving to an executable jar later.
- Who: agent runs the recipes; the owner of rung windows holds features whose area overlaps.
- Evidence: the dependency tree shows nothing below the target versions. No old-namespace imports after the jump (banned-API ratchet). Smoke passes.
- Unblocks: packaging.

**3.3 Replace a framework with no successor.** This is a **refactor inside in-place**. Do it handler by handler with branch by abstraction: mount the new framework on a sub-path alongside the old one, move handlers over one at a time with characterisation per handler, and delete the old framework's entry point at the end.
- Who: agent, one handler per slice.
- Evidence: the old framework's import count falls each slice and reaches 0; then its entry point is deleted and it is banned.
- Unblocks: packaging, and features that add handlers (held until now).

### Phase 4: packaging

**4.1 Self-contained executable.** Move from a server-deployed archive to a self-contained executable (an executable jar, a single binary, a wheel with an entry point). Resolve view technologies that do not survive the move, either by keeping a compatible packaging or by moving the views first. Externalise config into a config file plus environment variables.
- Who: agent.
- Evidence: the executable starts and passes smoke. No manual deploy-to-server step remains in docs or scripts.
- Unblocks: the container image.

### Phase 5: runtime container

**5.1 Container image.** A multi-stage Dockerfile on a supported base image for the target runtime. Config comes only from env. Add a health endpoint. Use a non-root user. Smoke runs **against the image**.
- Who: agent.
- Evidence: `docker build` in CI. `make smoke IMAGE=…` passes. The image is scanned (Trivy) and the scan is gated with a ratchet.
- Unblocks: the host move.

### Phase 6: host

**6.1 Move to the target host.** Move the image to the target host (VM with compose, ECS, App Service, k8s). This is the rehost "R", and it is cheap now because the earlier rungs made the artefact portable. Run the DB migration as a pipeline step before rollout.
- Who: agent builds the pipeline; a person signs off the prod cutover.
- Evidence: the pipeline deploys main to staging automatically. The `path to production` and `infrastructure` axes move to `supported`.
- Unblocks: the finish line.

### Phase 7: shape toward the target

**7.1 Declare modules and freeze the baseline.** Declare the modules of the recorded `Target` (`target-shape.md`) and freeze their existing violations as a ratcheted baseline. This is cheap and can come earlier, before the first feature, so that each feature already lands in a module.
- Who: agent drafts the module map; a person accepts it.
- Evidence: the module map is committed and the violation baseline is in the ratchet.
- Unblocks: features landing in modules; 7.2.

**7.2 Reshape this code.** After the finish line holds, reshape the code toward `Target`: break up the god facade and base class behind characterisation, move tables to module ownership, and remove one baseline entry per slice. A `Target` of `as-is` ends the ladder at the finish line. Growing *new* modules and retiring the old paths through the ledger, instead of reshaping the old code, is the strangler fig with its new home `inside` (`strangler-fig.md`): a different strategy, recorded by a new ADR.
- Who: agent, one baseline entry per slice; a person approves any `.approved` change.
- Evidence: the violation baseline shrinks each slice and never grows. Characterisation is unchanged.
- Unblocks: the code matching `Target`.

### Finish line
Done when the ADR's `Finish line` holds and every rung is `audited`. Audited means the old target is banned in the ratchet, the recipe is re-runnable with no diff (its dry run is empty), and smoke and characterisation are green on the final tuple. The pipeline deploys the image, and the `release mode` axis reflects actual practice. At that point the shape phase (7.2) starts if `Target` is not `as-is`, or a new ADR keeps the strategy in-place for maintenance (re-run recipes each LTS).

## 4. How a feature request is handled

These are the in-place rules the spec and plan must state per feature.

1. **Floor before features.** No feature slice starts until Phase 0 is green: secrets gone, build floor, smoke, characterisation of the feature's area, data baseline if the feature touches the schema, and the gate.
2. **Security rungs jump the queue.** If a layer has a known exploited CVE, or a library is still on an EOL branch, the rung that patches it (Phase 1) comes **before** the first feature, regardless of ladder order.
3. **Wait for a rung that would rewrite the area.** A feature touching area X waits for any rung that would rewrite X within the next rung window. Otherwise the feature is written twice, for example a new handler in a framework weeks before that framework is removed. Either schedule the rung first, or fence the feature (rule 4).
4. **Fence, if not waiting.** A feature that goes ahead of a rung must keep its logic out of the doomed layer. Put the domain service and query in plain code with no framework imports, test them, and keep a thin adapter in the old framework. The banned-API ratchet enforces this: new files may not import the doomed framework beyond adapters, or the old namespace once its jump is scheduled.
5. **Rung windows freeze the area, not the team.** While a rung slice is open, feature slices that touch files in the rung's blast radius are held. Features elsewhere proceed. For whole-app rungs such as the language version, keep the window short (one slice, hours to days) and rebase features after it.
6. **Recipe rungs run on a quiet trunk.** Merge open feature slices first, run the recipe, merge, then release features again. Recipes are re-runnable, so a conflict means regenerating, not hand-merging.
7. **A feature never carries a rung.** Do not bump the runtime "while I'm in there". The rung is its own slice with its own evidence.
8. **The spec names its rung prerequisites.** Each spec carries:
   - `Requires rungs:` e.g. `language≥<stepping stone>, web-framework≥<patched major>, data:baselined`. The plan must order slices so the prerequisites land first.
   - `Fence:` what the feature must not use.
   - `Rung window: <none|rung N>` the window, if any, the feature falls in.

Visibility: not applicable. The feature ships in the one deployable, so there is no routing or toggle between an old and a new system to decide.

## 5. How the method carries it

### Adoption sequence on the board
1. `slipwai adopt` → survey → convergence map, gate and ratchet installed.
2. **Decide.** The board's decide step is a form that asks exactly in-place's line: `Target:`. It writes the ADR with that line plus a derived `Build:` line, and commits it. The strategy record reads the accepted ADR's `Name: value` lines; a missing `Target:` is said by `check-convergence` and on the board, and the decision still stands.
3. **After the decision, before the constitution**, the adoption sequence (the board's voyage, and `slipwai adopt --next`) runs the build floor and then `smoke`.
4. The map's **Build** row (`undeclared → declared → pinned → reproducible → inventoried`) and **Platform** row (`unknown → inventoried → supported → audited`) are read off the tree and shown on the board.

### Draft, spec and mock-ups
- **`/draft`** reads the strategy and this playbook, and refuses while the decision is missing or incomplete. The constitution carries in-place's clause. Every spec ends with `## Strategy fit`, holding `Requires rungs:`, `Fence:` and `Rung window: <none|rung N>`. When the ADR's `Target:` is modular, the spec also holds `Module:`, `Publishes:`, `Consumes:` and `Owns data:`.
- A PRD line that contradicts the strategy is overridden in the spec and quoted beside the ADR line it contradicts.
- **Plan**: `/sail`'s plan stage holds each slice to in-place's rules (section 4). If a needed rung is large, the plan says whether the feature waits or fences, and why.
- **Mock-ups** show the feature inside the existing UI of the one deployable; there is no second UI to design for.

### Constitution
The draft writes in-place's clause into the constitution from the ADR. In substance:
- "One deployable, one codebase. No parallel system, no long-lived upgrade branch."
- "Platform changes are recipes first. Agents run the named recipe and commit its output separately from hand fixes."
- "Characterisation `.approved` files change only with a person's approval and a reason."
- "No feature slice carries a platform change, and no rung slice carries a feature."
- "New code may not use: <banned list>. New logic lives outside the framework layer scheduled for replacement."
- "Every schema change is a numbered migration after the baseline."
- "Security rungs pre-empt features."

### Gates
- `make verify` runs `check-convergence` and, in an adopted repo, `check-imports` through the ratchet: existing violations are a baseline, new ones fail. With `"layout": "modular"` on the adopted application, only `check-imports`' context-boundary rule applies.
- The build steps the programme names are read off the tree: an Ant build, a missing compile target, and a Java target no current JDK accepts (naming the newest JDK that still can, with `--release 8` as the stepping stone). The ratchet names a missing build tool correctly.
- `Requires rungs:`, `Fence:` and `Rung window:` are written by the draft and held by the plan stage; no gate checks them.

### Programme pacing
- The build floor comes first. Then the security fix, then one compatible combination of versions per slice, so each rung slice is small enough to land on its own. Stepping-stone versions are used rather than one giant jump.
- Cadence: alternate. After each rung lands, let feature slices run for a while before the next rung window. Exceptions: security rungs, and a coupled framework-generation tuple, which should be one concentrated window.
- Measure with DORA's four keys from git and CI: deployment frequency, lead time, change-fail rate and time to restore should not get worse during rungs. If change-fail climbs, shrink the rungs.

### Ledgers
There is no retirement ledger, because nothing is retired route by route: the one system is upgraded where it stands. The convergence map plays the ledger's part: its Build and Platform rows say how far the one deployable has climbed, read off the tree. In the shape phase, the `check-imports` baseline is the record of what is left to fix, and it may only fall.

**Not built yet:**
- A banned-API ratchet (the count of old-API, old-namespace and doomed-framework uses).
- Checking the dependency tree against the declared coupled-rung tuples.
- A gate that checks `Requires rungs:` and `Fence:` (the draft writes them; nothing enforces them).
- A per-rung gate (recipe dry-run empty, characterisation unchanged, smoke on the new tuple).
- Per-module "strict" (no baseline) and privacy rules, and a data-ownership check over SQL, ORM and stored procedures.
- Baseline burn-down tracking on the board.
- Toolchain-needs detection beyond Java targets (other ecosystems' wrappers, toolchain files, machine tool checks at survey time).

## 6. Anti-patterns and how the method detects each

| Anti-pattern | Detection |
|---|---|
| **Upgrade branch**: a months-long runtime-upgrade branch | Branch age check in `/survey` or cruise. Rung slices must merge to main. The board flags rung cards open for more than N days. |
| **Hand-migrating what a recipe does** (agent edits 300 files manually) | The plan names a recipe ID. The slice evidence must include the recipe commit, and the recipe's dry run must be empty afterwards. |
| **Skipping rungs** (oldest runtime straight to newest, with the old framework still in place) | Coupled-rung tuples in the ADR. The gate checks the dependency tree against the declared tuple for the current rung. |
| **Feature written into the doomed layer** | Banned-API ratchet on new files. `Fence:` in the spec. |
| **Feature carrying an upgrade** | The slice diff touches the language level, a framework version or a recipe together with feature code. The gate rejects it via a "rung files" path list. |
| **Changing approved files to make it green** | `.approved` diffs require a person's sign-off line in the slice notes. The gate counts approved-file changes. |
| **Code before smoke** | The floor lane blocks feature and rung cards until `make smoke` has passed in CI. |
| **Schema drift via ORM auto-update** | A config grep in verify. The data axis cannot reach `supported` while it is set. |
| **Rung that is really a rewrite** | A rung red for more than 3 attempts, or diff size far above the recipe's output. That prompts a `/wdyt`-style question to the person: "re-strategise?" |
| **Security rung deferred behind features** | A known-CVE dependency (dependency scanner) with a feature card ahead of its rung on the board. The board warns. |
| **Finishing on paper** (rung marked done, old API still present) | `audited` requires the banned count to be 0 and the recipe dry-run to be empty. |

## 7. Worked example: an internal booking app

The app is an internal room-and-equipment booking web app, one deployable, a few tens of thousands of lines. It runs on an end-of-life language runtime and an end-of-life web framework with published security advisories. It has a hand-rolled build with vendored libraries, no tests, database credentials committed in config, and absolute file paths for uploads. The first feature is a **reminders panel on the dashboard**: "your bookings in the next 7 days".

**Strategy reasoning:** one deployable, a modest size, and a domain (rooms, bookings, people) that users are happy with. Upgrade recipes exist for the runtime. The web framework's line is EOL with known advisories, which sets a security clock. The panel is a read-only query plus one view fragment. In-place fits.

**ADR excerpt**
```
Strategy: in-place
Ladder: runtime old→stepping stone→current LTS ; web framework EOL line→last patched major→(replace with mainstream successor) ; ORM to last compatible major→current ; archive→executable ; image ; host
Coupled rungs: (stepping-stone runtime, minimum framework versions that load on it) ; (current runtime, new framework generation, new ORM, new namespace)
Feature interleave: fence for the reminders panel; rung-window for anything adding web-framework handlers
Security clock: web framework EOL with published advisories; runtime EOL
Data: Flyway, V1 = production schema as of adoption
Finish line: current LTS runtime, supported framework majors, executable artefact, container, deployed by pipeline
```

**First ~10 steps**

1. **Secrets and paths (quick win).** Move DB and mail credentials to env plus a `config.example` file. The upload path becomes a config key with a default. A **person** rotates the DB password. *Evidence:* the secrets check passes and a grep for absolute paths is empty. *Unblocks:* fleet access.
2. **Build floor.** Replace the hand-rolled build with the ecosystem's dependency manager and wrapper. Map vendored libraries to coordinates **at the same versions**. Any module on a language level the current toolchain refuses moves to the lowest level it accepts. *Evidence:* a clean-checkout build passes, the vendored directory is gone, and the bundled-dependency diff against the old artefact is limited to known coordinates. *Unblocks:* recipes and dependency scanning.
    - Caveat: this step quietly moves the runtime forward. If an old library fails to load on it, the build-floor slice bumps that library to the last release of its current major. That is the first coupled-rung decision, recorded in the slice notes.
3. **Smoke.** Start the app headless with an embedded server or container, against a docker-compose database seeded from the baseline (step 4) and a small fixture set. `make smoke` checks: landing page returns 200, login as a fixture user, one known booking is shown. *Evidence:* the smoke job is green in CI. *Unblocks:* code changes.
4. **Data baseline.** Export the prod schema to `V1__baseline.sql`. A person baselines prod and shared databases. ORM schema auto-update is set to `validate`. *Evidence:* the CI DB is built from migrations and smoke passes. *Unblocks:* a future index migration if the panel needs one.
5. **Characterise.** Approval tests for: the dashboard HTML (scrub dates and session IDs), the booking handlers (golden-master their rendered output against fixtures), the ORM mappings (load each entity and dump it to JSON), and existing date handling (the panel will rely on it: time zones, day boundaries, recurring bookings). A person approves the `.approved` files. *Evidence:* approved files are committed and the safety-net axis is `inventoried`. *Unblocks:* rungs and the panel.
6. **Gate.** `make verify` runs build, tests, characterisation, smoke, the secrets check and a banned-API ratchet that baselines current uses of the EOL framework. *Evidence:* green on main, ratchet baseline committed. *Unblocks:* fleet slices.
7. **Security rung: the first stepping-stone tuple.** Run the runtime recipe to the stepping stone, then move the web framework to its last patched major and the ORM to its last compatible major. These are separate slices in one rung window, each gated by characterisation and smoke. Section 4 rule 2 puts this **before** the feature, because the panel adds a new surface to an app whose web layer has known advisories. *Evidence:* the dependency tree shows the patched majors, the dependency scanner shows no critical CVEs (or they are ratcheted), and characterisation is unchanged.
8. **Feature: reminders panel (fenced).** Spec says `Requires rungs: language≥<stepping stone>, web-framework≥<patched major>, data:baselined (read-only)`. `Fence: no logic in the web framework; no old-namespace imports outside adapters; standard-library date/time only`. It is split into slices:
    - 8a A plain `UpcomingBookings` service with unit tests for day boundaries, time zones and the week wrapping across a month or year end.
    - 8b A read-only query over existing booking columns. No schema change, unless the plan shows an index is needed (then `V2__index`).
    - 8c A thin handler in the current framework plus a view fragment on the dashboard. The dashboard approval file changes **once, intentionally**, with a person's approval.
    - The panel lands on the stepping-stone tuple *now*. It does not wait for the framework replacement, because the fence leaves only a few lines of framework code to move later.
9. **Language rung to current LTS.** Run the recipe on a quiet trunk (merge the panel first). Run on the new runtime at the old language level first, then raise the level. *Evidence:* the target level is declared, smoke runs on the new runtime, and characterisation and panel tests are unchanged.
10. **The framework-generation tuple.** Move the application framework, ORM and namespace together in one concentrated window, wrapping before repackaging. Replace the EOL web framework by branch by abstraction: the new framework serves migrated handlers on a sub-path, and handlers move one per slice, **the reminders panel adapter first**, as the proof (it is the thinnest). The old framework's entry point is deleted when its import count hits 0. Features that would add old-framework handlers are held (rung window). Then packaging (Phase 4), image (Phase 5), host (Phase 6).

**Where the panel fits:** after the floor (1 to 6) and the security tuple (7). Before the LTS runtime and before the framework replacement, but fenced so that those rungs move it cheaply. If the business had a hard date sooner than step 7 could land, the fallback is to ship the panel on the unpatched framework behind the same fence. That fallback should be recorded as a QUESTION or accepted risk, not done silently.
