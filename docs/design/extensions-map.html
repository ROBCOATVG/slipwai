How an extension gets into a project, and where it is allowed to act

An extension is optional dev tooling a project elects at ./init. It never changes generated code, which is the line between it and a language or a target. It is a package like the others, found and installed the same way, and it reaches the workflow through exactly three kinds of attachment: hooks at closed points, guards in front of tool calls, and tools a headless session is allowed to reach.

The journey, left to right

the keelinside the projecta session or captaina persona file written

Four lanes, four moments. The package is written and published once; the machine installs it once; every project generated after that carries its files and offers it at ./init; and from then on it only ever runs where a point fires, a guard is consulted, or a gate runs. Nothing in a generated project imports slipwai: everything the project runs is a toolkit script shipped with it.

What extension.json declares

FieldWhat it is
key · nameWhat a person types (./init --extension codegraph) and what the menu shows.
description · tagsWhat the menu says under it, and what slipwai search matches.
ignoregitignore text for the local state it leaves, written into the project's .gitignore.
hooksWhich closed points it attaches a script to: {"init": "init.py", "after-stage": {"run": "hooks/sync.py", "stages": ["implement"]}}.
guardsWhich tool calls it may refuse, and in whose words it explains itself.
toolsThe tool names a headless session must be allowed, such as mcp__codegraph__*. The fact belongs to whoever brings the tool, not to the harness registry.

Everything beside the manifest is copied into the project at generation, under scripts/extensions/<key>/, so ./init can run it with no keel present. The manifest stays behind: it is read by the keel, which is the one place that cares.

The six obligations the entry point is held to

  1. Idempotent. Running the election twice does what running it once did. Files are written whole, never appended.
  2. Non-fatal. A tool that is not on this machine is a message and a clean exit, never a failed ./init.
  3. Projects. Its AGENTS.md block sits between <!-- extension:<key>:begin --> and :end, so re-projection replaces exactly that.
  4. Gated. Anything that can go stale, an index or a cache, ships a check-<key>.py that make verify runs.
  5. Recovers. Every message about a problem names the command that fixes it.
  6. Merges. Everything outside its markers is a person's and stays exactly as it was.

python -m slipwai.conformance --extension <dir> runs four of them against a scratch project and reads the other two; slipwai package new <key> scaffolds one that passes all six on day one.

Hooks: the closed set of points

PointFires
initOnce per election, from ./init --extension <key>. The entry point installs what it needs.
projectEvery re-projection: make agents, migrate, ./init --integration. Writes the AGENTS.md block and each harness's MCP file.
checkOn make verify, as one more gate. The only point that may fail anything.
before-stage · after-stageAround each rung of the ladder, from the captain, with the stage, slice, fairway and berth.
boundaryAt every captain boundary, after the inbox is read.
before-merge · after-mergeOn the rebased branch before the full gate, and once the slice is on trunk, from the harbourmaster.
before-compact · after-compactAround a harness compacting its context.

A hook is a second belt. It is reported, never fatal: a hook that fails is a hook line in the deck log naming the extension, the point and the last thing it printed, and the rung completes. The captain's own controls work with every hook removed. slipwai hooks prints the set with what is attached.

Guards and tools: the two other attachments

Guards may refuse a tool call

A guard runs in front of one call, from session.py at the harness's own moment, and refuses it by exiting 2; what it printed is what the agent is told, and the agent does something else. Anything other than exit 2 is a hook's behaviour: said, and the call goes ahead. Points: before-search, before-write, before-command, before-fetch, before-stop.

Because a guard refuses things a person asked for, it is agreed to separately: ./init asks once (guards.py --offer) over the elected extensions, and only the agreed ones are written to .slipwai/guards.json. Installed is not the same as agreed.

Tools let a headless session reach it

A captain's /sail session runs under an allow-list. An extension's tools are added to that list at election (.slipwai/hooks.json carries them), so a delegate can call the MCP server the extension brought. Nothing is validated against a harness: a pattern is a string in the harness's own spelling.

The files an election leaves

  • .slipwai/hooks.json — which extensions, by point, in firing order, plus their tool names. A controlled file: a run that edits it is refused.
  • .slipwai/guards.json — the guards a person agreed to.
  • .slipwai/extensions.json — what was elected, read by every re-projection.
  • AGENTS.md — the marker-fenced block, and each harness's project MCP file where a tool was declared.

Three ways a project elects one

  1. The menu. ./init shows a checkbox list built from available.json, the catalogue the generator wrote from the packages installed on the machine at generation. What is offered is what the project can actually run.
  2. A quickstart. A project generated from a quickstart carries .slipwai/quickstart.json naming the extensions it elects and the guards already agreed to; elected.py hands those to ./init and no menu appears.
  3. Later, by hand. ./init --extension <key> at any time, repeatable; a re-election is the same as the first, which is what obligation 1 is for.
