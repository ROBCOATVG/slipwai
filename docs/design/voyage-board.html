Three bands, top to bottom: the passage (the stages from PRD to accepted work), the model (the event model, with each slice's standing on it), and the work (slices by what the deck logs say). Nothing on it is a status field anybody typed: every state is derived from a file that exists, a marker that is gone, or a log line that was written, the same rule the toolkit already lives by.

The "working" column is the one thing the tree cannot tell on its own, so it comes from the two things the board already knows: its own child (init, draft, launch) and the fleet's heartbeats. That is also why "waiting on you" is loud and "working" is quiet: a stalled captain and a finished one look the same in a status field, and only the log tells them apart.

Shape of the implementation

  1. passage.py, a reading like next_steps.py: one function returning the eight stages with state, evidence and the next command. It reuses template_gone, the spec glob, the chart reader and the fleet's fold. Nothing writes.
  2. /voyage and /voyage.json on the bridge: the page, and the payload the page polls at the cadence /init.json already uses. The fitting's receipt is folded into stages 2–6 so the strip moves while a child runs.
  3. The model band is draw.io's viewer script, vendored into the keel's assets and served as a route like the manifest and worker, so it draws offline. The board reads model.drawio, runs make model-drawio first when model.yaml is newer, and rewrites the style of each slice's caption cell — found by the deterministic id the renderer gives it — from the same fold band 3 uses. The committed file is never written.
  4. The fitting card folds Claude Code's stream-json to assistant text, keeping the usage counts on the chip. A small change in init_run.read: a line that parses as JSON with a message.content is replaced by its text.
  5. The button moves from the Made card to the strip's current stage, and on the event profile reads "Model it next" instead of "Continue the build", linking the modelling conversation rather than launching.
  6. Tests mirror the existing ones: a tree with files at each stage asserts the strip, a fake fleet asserts the columns, and the served page asserts the payload. Byte gates are untouched: nothing generated changes.

Decisions this design makes

  1. A tab, not a card. The Board stays the operations view (streams, speed, inbox); Voyage is the "where are we" view. One link each way, and the Made card after a generate lands on Voyage, since that is the question a person has at that moment.
  2. Three states plus "waiting on you". Done, working, to do are the strip's; waiting is a fourth because it is the only one that asks for a person, and it should look like it.
  3. The event model stage is profile-specific. On the standard profile it is drawn faint and skipped, not hidden, so both profiles read the same strip.
  4. drawio is shown, not drawn. The viewer renders the committed file rather than a second picture, so what the board shows is what a person opens in draw.io. The one addition is a border, and the one thing it refuses is editing: an edit there would drift from model.yaml and fail the gate on the next commit. The diagram keeps draw.io's colours in both themes, which a diagram is allowed to.
  5. No kanban drag. Columns are read-only: moving a card would be a status field by another name. The one action in band 3 is Tell the stream, which already exists.
  6. Type. IBM Plex Sans for the page and Plex Mono for every identifier — paths, marks, fairways — so a thing you can type looks like one. The board's current system stack remains the fallback; the palette is the board's own tokens plus one critical hue.
