# Tools required

Scaffolding needs almost nothing; a generated repository needs whatever its own toolchain needs. Nothing
here is installed for you, and nothing is vendored into the output.

| To do this | You need |
|---|---|
| Run `slipwai generate` (an installed `uv`/`pip` tool) | Python 3.11+ and Git (CI runs 3.13) |
| `make verify` on the factory itself | The above, plus network access on first run: it installs the pinned ruff from `requirements-dev.txt` into an ignored `.python-tools`, then every supported backend toolchain — Node and npm, `uv`, Go, a JDK — because the suite generates every variant and runs its native gate |
| Run a packaged `slipwai` executable | Git only — the executable embeds Python |
| `slipwai generate --target aws` (and the interactive form choosing `aws`) | The above, plus what its `./init` will use: OpenTofu 1.12 (`tofu`), the AWS CLI, a region (`AWS_REGION`, or `aws configure set region …`), and `gh` on the PATH or `GITEA_TOKEN` set. Checked when the target is chosen; refused with install pointers if missing, `--skip-checks` if another machine will run `./init` |
| `slipwai generate --target azure` (and the interactive form choosing `azure`) | The above, plus what its `./init` will use: OpenTofu 1.12 (`tofu`), the Azure CLI (`az`), a region (`AZURE_LOCATION`, or `az config set defaults.location=…`), and `gh` on the PATH or `GITEA_TOKEN` set. Checked when the target is chosen; refused with install pointers if missing, `--skip-checks` if another machine will run `./init` |
| `./init` in an `aws` project | Everything the project's README lists under *Before `./init`*: `tofu` (OpenTofu 1.12); the `aws` CLI signed in as an **administrator** of the account; a region (`AWS_REGION`, or `aws configure set region …`); the forge — `gh` signed in for GitHub, or `GITEA_TOKEN` with `read:user` and `write:repository` (plus `write:organization` for an organisation's repository) for Gitea; the URL the repository will live at; and somewhere to keep the passphrase `make bootstrap` prints once. Missing a tool, it installs Spec Kit as usual, says what is missing and leaves the push and bootstrap for `./init --repository <url>` or `make bootstrap` later |
| `./init` in an `azure` project | Everything the project's README lists under *Before `./init`*: `tofu` (OpenTofu 1.12); the `az` CLI signed in as an **Owner** of the subscription — Owner rather than Contributor because the bootstrap grants the pipeline its roles; a region (`AZURE_LOCATION`, or `az config set defaults.location=…`); the forge — `gh` signed in for GitHub, or `GITEA_TOKEN` with `read:user` and `write:repository` (plus `write:organization` for an organisation's repository) for Gitea; the URL the repository will live at; and somewhere to keep the passphrase `make bootstrap` prints once. A project that answered `--auth entra` also needs the person running it to be a Privileged Role Administrator, because an app registration is a directory object rather than a subscription resource. Missing a tool, it installs Spec Kit as usual, says what is missing and leaves the push and bootstrap for `./init --repository <url>` or `make bootstrap` later |
| `make verify` in a TypeScript backend | Node 22.13+ (CI runs 24) and npm |
| `make verify` in a Python backend | `uv` on the PATH, which is this backend's whole toolchain — it builds the environment from the committed `uv.lock` and fetches a Python if the machine has no suitable one. `scripts/verify` says how to install it if it is missing; CI installs the pinned version from PyPI |
| `make verify` in a Go backend | Go 1.26+, which is what the module's `go` directive says: staticcheck is a `tool` dependency of every variant and requires it. Network access on the first run, so `go mod download` can fetch it and the store's driver; nothing else is installed |
| `make verify` in either Java backend (`java-quarkus`, `java-spring`) | A JDK 25, and nothing else — the same answer for both, because the wrapper belongs to Maven rather than to whichever framework owns startup: the project commits `./mvnw`, which fetches the Maven pinned in `.mvn/wrapper/maven-wrapper.properties` on first use. The wrapper is the `-Dtype=only-script` kind — three text files, no `maven-wrapper.jar` — because `assets/` carries text only. Its one-off download needs network access, or a `~/.m2/wrapper/dists` already holding that Maven |
| `make verify` with a `react-vite` frontend | Node and npm, whatever the backend language is |
| `make model` in the event profile | Node and npm, plus a Chromium that Puppeteer can drive |
| `make mutation` | Whatever that backend's mutation tool needs, and only two backends have one wired up. **Go**: Python 3 and Go 1.25+ — the recipe is `scripts/go-mutation.py`, which stages the service beside the workspace modules it imports and runs Gremlins 0.6.0 through `go run`, so the tool is never a dependency of the module it mutates and is fetched on first use. **Java Spring**: the JDK and `./mvnw`, which fetch PIT's Maven plugin the same way. **Quarkus** ships a documented placeholder instead, because PIT times out on `@QuarkusTest`; **TypeScript** and **Python** exit 2 asking for the mutator to be configured first — a checked-in Stryker configuration, or `mutmut` on the PATH |
| `make dev` in a project with an HTTP transport | That backend's own toolchain — the same one `make verify` needs |
| `make dev-web` with a `react-vite` frontend | Node and npm |
| `make demo` — the whole app in containers | Docker with Compose v2, and nothing else: each toolchain runs inside its container |
| `make services-up`, `services-down` in a project with containers — which the default `postgres` store makes one | Docker with Compose v2 (`docker compose`) |
| `make migrate`, `test-integration` with `postgres` selected | The above, plus that backend's own toolchain — Node and npm for TypeScript, a JDK for Java |
| `make check-model`, `check-imports`, `check-migrations`, `check-flags`, `check-extensions`, `check-speckit`, `check-codegraph`, `check-constitution`, `check-styles`, `agents` | Python 3 — no third-party packages |
| `make build`, `smoke-image` in an `aws` or `azure` project | Docker, plus the backend's image builder: `pack` (0.40) for TypeScript and Python, `ko` (0.19) for Go, nothing beyond the JDK for either Java backend — Quarkus's Jib extension and Spring's `build-image` are Maven goals. A daemon using the containerd image store cannot export a `pack` build; set `IMAGE_REGISTRY` so `pack` publishes instead |
| `make push`, `deploy`, `rollback`, `migrate-remote`, `url` in an `aws` project | The above, OpenTofu 1.12 (`tofu`), the `aws` CLI, AWS credentials, and `AWS_REGION` and `TOFU_STATE_BUCKET` in the environment — the bootstrap stack's outputs |
| `make push`, `deploy`, `rollback`, `migrate-remote`, `url` in an `azure` project | The above, OpenTofu 1.12 (`tofu`), the `az` CLI and an Azure sign-in; `npx` where the project has a browser app, for the Static Web Apps CLI the site is uploaded with. The identifiers come from the environment or from the `infra/` files `make bootstrap` wrote |
| `make verify` on the factory, for the `aws` suites | `tofu` and `ko` on the PATH, or those tests skip with the reason; network for the pinned AWS provider once |
| `make verify` on the factory, for the `azure` suites | `tofu` on the PATH, or those tests skip with the reason; network for the pinned azurerm, azapi and azuread providers once |
| `./init` (installs Spec Kit) | `uv`, or Python 3 with network access; Spec Kit 0.16+ for the preset layer |

The gate scripts a generated repository ships are deliberately dependency-free: they use only the Python
standard library, so `make verify` needs no `pip install` of its own in any language.
